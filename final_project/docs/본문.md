## 1. 연구 목적 및 보고서 범위

스마트모빌리티공학실험2 **중간 프로젝트**에서는 실측 UWB·Wi-Fi 거리 데이터를 이용한 실내 2D 측위를 수행하였고, **기말 프로젝트**에서는 인공 생성 셀룰러 RTT 데이터(`InF_DH_FR1.mat`, 채점명 `DH_FR1.mat`)와 18개 기지국 기하 정보로 700명(학습) + 300명(hidden) 사용자 위치를 추정한다.

본 보고서는 다음을 목적으로 한다.

1. 중간 프로젝트 전 기간의 **시행착오·통찰**을 재현 실험(2026-05-19 일괄 재실행)을 통해 정리한다.
2. 교수님께서 강조하신 **“성능 숫자보다 개발 과정과 학습 내용”**을 중심으로 서술한다.
3. 기말 데이터 분석 결과를 바탕으로 **중간에서 얻은 방법을 무엇을 이관하고, 무엇을 버릴지** 연구 계획을 제시한다.

**재현 조건:** `midterm_project/outputs`를 초기화한 뒤 파이프라인 V1~V16·JWT 총 25개 스크립트를 `scripts/rerun_all_pipelines.py`로 순차 실행하였다(총 소요 약 33분). 이전에 `outputs`에 남아 있던 V15 부가 실험 산출물(`v15_custombias_*`, `v15_reportbias_*` 등)은 코드 수정 과정에서 누적된 것으로, 이번 재실행에서는 **단일 `v15_summary.json`** 만 생성되도록 정리하였다.

## 2. 중간 프로젝트 문제 정의 및 데이터 특성

### 2.1 문제 정의

- **입력:** 6개 UWB + 6개 Wi-Fi 앵커의 거리 **중앙값·분산**(Train 270행, Validation 100행).
- **출력:** 타일 좌표 기반 실내 2D 위치 (`True = Node × 0.6 m`).
- **최종 제출 파이프라인:** **V15** (`indoor_fusion_pipeline_v15.py`, `defensive` 프로필).

### 2.2 실측 데이터의 한계 (UWB)

`sensor_spatial_profiler` UWB 순차 필터를 재실행한 결과(Train, long-format):

| 단계 | 레코드 수 | 제거 |
|------|-----------|------|
| Stage 0 (유효 UWB) | 1176 | — |
| Stage 1 (Hard limits) | 1149 | 27 |
| Stage 2 (분산 < 17) | 801 | 348 |
| Stage 3 (MAD/앵커) | 707 | 94 |

필터 후에도 앵커별 평균 오차(측정−진값)는 **−0.8 ~ −3.6 m**이며, 풀 MAE **2.83 m**, P90 **6.83 m**에 달한다. 즉 **기기 이상·오측정·결측**이 많아 “정제만으로 깨끗한 UWB”를 얻기 어렵다는 것이 실험적으로 확인되었다.

**그림 삽입:** `fig05_uwb_filter_funnel.png`, `fig05b_uwb_filter_profiler.png`

Train CSV 원시 점검(270행): UWB 결측 약 **27%**, 음수 거리 존재, 컬럼명 오기(`d1044709` 식별 불가 등). 이 때문에 파이프라인은 `fusion_realtime_sanitize.py`로 **행 삭제 없이** 보간·캡만 적용하는 방향을 택하였다.

### 2.3 Wi-Fi는 상대적으로 안정적 “바닥”

여러 버전에서 **Pure Wi-Fi 삼변측량** 검증 RMSE는 **1.55 m 전후**로 수렴한다(V8·V9·V10·V11 재실행 일치). 이 수치가 이후 알고리즘 설계의 **기준선(baseline)** 이 되었다.

## 3. 개발 과정: 시행착오와 통찰 (V1 → V15)

아래 수치는 **2026-05-19 재실행** `batch_rerun.log` 및 `*_summary.json` 기준이다. 튜닝 방식에 따라 공정 비교가 달라짐을 반드시 구분한다.

### 3.1 Phase 1 — UWB를 믿었을 때의 실패 (V1~V7)

| 버전 | 대표 검증 RMSE | 시도 | 결과·통찰 |
|------|----------------|------|-----------|
| V1 | Wi-Fi 2.04 m / **전체 7.31 m** | KNN + 융합 | UWB 융합이 오히려 성능 **파괴** |
| V3 | Wi-Fi 1.49 m / **Hybrid 4.39 m** | Wi-Fi+UWB 동시 융합 | 하이브리드가 Wi-Fi만보다 **나쁨** |
| V6~V7 | Step C **3.5~4.0 m** | 분산 가중·HBB 등 | UWB 노이즈 속에서 그리드 튜닝해도 **바닥 회복 불가** |

**통찰 ①:** 실측 UWB는 “추가 정보”가 아니라 **강한 노이즈원**이다. 정제 파이프라인을 거쳐도 기하 게이트 없이는 측위에 쓰기 어렵다.

### 3.2 Phase 2 — Wi-Fi 가이드 전략 (V8~V11)

**V8 애블레이션**이 결정적 근거가 되었다(재실행):

| 모드 | 검증 RMSE |
|------|-----------|
| Pure Wi-Fi | **1.55 m** |
| Pure UWB | **7.11 m** |
| Hybrid (HBB) | **3.51 m** |

**그림 삽입:** `fig04_v8_ablation.png`

- **V9:** Wi-Fi 1차 추정 후 UWB 기하 게이트 융합 → Step B **1.47 m**. 그러나 게이트 임계를 **검증 RMSE 그리드**로 고름 → **데이터 누수(낙관 편향)**.
- **V9 strict:** 게이트만 Train K-Fold로 선택 → Step B **1.62 m**. 무결하지만 수치는 올라감 → **공정한 평가의 중요성** 학습.
- **V10:** 검증 홀드아웃에서 K=28로 KNN 선택 → Step D 1.74 m. Step C(1.80 m)보다 나으나, **검증 라벨로 K를 고른 것**은 기말 hidden set에 일반화되기 어렵다는 교훈.
- **V11:** IRLS·KNN을 검증 그리드로 조합해도 Step C ≈ **1.55 m**로 Wi-Fi 바닥과 동일 → **복잡도 증가 ≠ 성능**.

**통찰 ②:** Wi-Fi 가이드는 실내·실측 UWB 환경에서 **유일하게 안정적인 1차 좌표**를 제공한다. 그러나 검증셋 튜닝은 “좋은 숫자”를 만들 뿐 **연구 무결성**을 해친다.

### 3.3 Phase 3 — 무결 튜닝과 V15 확정 (V12~V16)

| 버전 | Step C (또는 최종) RMSE | 튜닝 |
|------|-------------------------|------|
| V12 | **1.445 m** | 검증 그리드 (**누수**) |
| V12 Turbo | **1.441 m** | Train CV + Optuna |
| V13 | **1.444 m** | Train CV + Optuna |
| V14 (JWT) | **2.228 m** | 팀원 Wi-Fi 보정 아이디어 → **실패 기록** |
| **V15 HardGate** | **1.462 m** | Train OOF 게이트 + Optuna (**최종**) |
| V16 | HardGate **1.827 m** | 목적함수 실험 분기 → V15 대비 악화 |

**그림 삽입:** `fig03_midterm_evolution.png` (전체 진화), `fig06_v15_stages.png` (V15 단계별)

**V15 재실행 상세 (defensive):**

| 단계 | 검증 RMSE | 검증 MAE |
|------|-----------|----------|
| Wi-Fi-Guide (Step A) | 1.574 m | 1.134 m |
| Fusion-HardGate (Step B) | **1.462 m** | 1.175 m |
| Fusion-ReWeight (Step C) | 1.475 m | 1.181 m |

- Train CV: Wi-Fi-Guide **2.62 m**, Fusion-ReWeight **2.54 m** — 검증보다 높아 **분포 차이·과적합 여지** 존재.
- 선택 하이퍼(요약): 게이트 **2.54 m**, UWB 분산 inflate **14.3**, fusion Huber **1.0**, IRLS 임계 **3.05 m**, Wi-Fi 캘리브 **identity**.
- **HardGate가 ReWeight보다 우수** → UWB가 불안정할 때 **과도한 IRLS 재가중**보다 **기하 게이트로 채널 제거**가 낫다.

**통찰 ③:** 최종 V15는 (1) **v12 검증 그리드 미사용**, (2) **Train OOF로 게이트 구간**, (3) **Optuna는 Train CV만** 이라는 무결성을 갖춘다. 성능 1.44~1.46 m대는 “튜닝 트릭”이 아니라 **Wi-Fi 바닥 + 제한적 UWB 융합**의 결과로 해석한다.

**통찰 ④ (V14):** JWT/Isotonic 등 **복잡한 Wi-Fi 보정**을 얹으면 오히려 악화(2.23 m). 기말에서도 “모델 복잡도”보다 **문제에 맞는 단순 구조**를 우선할 것.

## 4. V15 최종 알고리즘 요약 (재현 기준)

1. **Wi-Fi-Guide:** Train CV로 순위 매긴 V3 프로필 + Wi-Fi 캘리브 카탈로그 → 강건 Wi-Fi 삼변.
2. **Fusion-HardGate:** Train K-Fold OOF 잔차로 UWB 게이트 τ 구간 추정 → Wi-Fi 가이드 대비 UWB 기하 잔차가 큰 채널 **하드 제거** 후 융합 삼변.
3. **Fusion-ReWeight:** Huber + IRLS(Tukey) 잔차 재가중 (V15에서는 HardGate보다 소폭 불리).

**의도적으로 버린 것:** 검증 라벨 기반 그리드, v15_custombias 등 **코드 개발 중 생성된 부가 실험 산출물**(이번 outputs 정리로 제거).

## 5. 기말 프로젝트 데이터 분석 (`InF_DH_FR1.mat`)

### 5.1 데이터 구조

| 변수 | 크기 | 비고 |
|------|------|------|
| `p` | (2, 700) | 학습용 GT 위치 |
| `d_hat` | (18, 700) | RTT |
| `BS_positions` | (2, 18) | 명세의 `p_bs`에 해당 |
| `indices` | (700,) | UE 인덱스 |

채점 시 300명 hidden이 추가되므로 `main.py`는 **동적 `num_user`** 필수.

### 5.2 EDA 요약

**그림 삽입:** `fig01_final_dhat_vs_dtrue.png`, `fig02_final_spatial_layout.png`

| 지표 | 값 |
|------|-----|
| d_true vs d_hat 상관 | **0.815** |
| 잔차(d_hat−d_true) 평균 | **+15.9 m** |
| 잔차 표준편차 | **20.2 m** |
| Huber LS 삼변 (700명) RMSE | **19.25 m** |
| Huber LS 중앙값 오차 | **14.51 m** |

**해석:**

- 중간의 “실측 UWB 지옥(7 m대)”과 달리, 기말 RTT는 **기하 거리와 상관이 있다** → **가공·합성 데이터**로서 알고리즘이 먹을 구조가 있다.
- 그러나 **전역 bias·스케일 왜곡**이 커서 naive 삼변만으로는 19 m대 → **기지국별 보정·학습 매핑**이 필요.
- 영역이 넓음(x 약 ±60 m) → 중간 실내 타일(12×18 m)용 하드코딩 bias·경계는 **이관 불가**.

상세 수치: `final_eda_stats.json`

## 6. 중간 통찰 → 기말 적용 매트릭스

| 중간에서의 요소 | 기말 적용 | 비고 |
|-----------------|-----------|------|
| Wi-Fi 가이드 2단계 | **미사용** | 단일 RTT 관측; “가이드 센서” 없음 |
| UWB 기하 HardGate | **개념 이관** | 18 BS RTT 이상치·잔차 기반 **채널 마스킹** |
| Huber / IRLS 삼변 | **그대로** | `scipy.optimize` 초기값 + 강건 손실 |
| 앵커별 거리 보정(identity 최적) | **학습 보정층** | 18채널 affine/MLP로 RTT 보정 |
| Train K-Fold + Optuna | **`train.py`에 구현** | 700명 내부 CV, hidden 대비 |
| 검증셋 튜닝 | **금지** | 기말 report.md 공정성 논의용 |
| KNN 잔차 (V10) | **신중** | 700명에서 과적합 위험; CV 필수 |
| PHASE1 고정 bias | **미사용** | 합성 데이터에 부적합 |
| V14 JWT 복잡 보정 | **참고만** | 단순 구조 우선 |

### 6.1 기말에서 “학습”을 쓰는 이유 (중간과의 대비)

중간에서는 UWB **기기 이상·오측정** 때문에 지도 학습이 오히려 **노이즈를 외워** hidden에 악화될 위험이 컸다. 기말 데이터는 **합성·상관 구조가 명확**하고 GT 700명이 제공되므로:

1. **RTT → 보정 거리** 회귀(채널별 또는 공유 MLP),
2. **보정 거리 → (x,y)** 강건 삼변,
3. (선택) **end-to-end** `(d_hat, p_bs) → p` PyTorch

를 `train.py`에서 학습하고, `main.py`는 학습 가중치 로드만 하도록 계획한다.

## 7. 기말 프로젝트 연구 계획

### 7.1 목표

- Hidden 300명 **RMSE 최소화** (10분 제한 내).
- `report.md`: 중간 실험 **고찰 → 알고리즘 도출** 서술, Agent AI 역할 구분, **공정한 baseline** 비교.

### 7.2 알고리즘 로드맵 (3안)

| 안 | 구성 | 장점 | 리스크 |
|----|------|------|--------|
| **A (주력)** | 학습 RTT 보정 + Huber 삼변 + BS 마스킹 | 중간 V15 철학과 연결, 해석 가능 | 보정 과적합 |
| **B** | E2E MLP / 작은 CNN on (d_hat, BS) | 표현력 | baseline unfair 논란 |
| **C** | Huber LS + CV 튜닝만 | 빠른 baseline | 상한 낮을 수 있음 |

**1차 구현 순서:** C → A → (필요 시) B.

### 7.3 마일스톤

| 주차 | 작업 | 산출 |
|------|------|------|
| 11주(본 보고서) | 중간 재현·기말 EDA·계획 | 본 문서 + 그림 6종 |
| 12주 | `train.py` v0: 보정+삼변, 5-fold CV | 내부 RMSE 표 |
| 13주 | Optuna/마스킹 튜닝, `main.py` 연동 | `model.pt` |
| 14주 | hidden 대비 점검, `report.md` | GitHub 제출 |

### 7.4 공정한 평가 설계

- **Baseline:** 동일 `d_hat`, `p_bs`에 Huber LS 삼변 (학습 없음).
- **제안:** 학습 보정 + 강건 삼변 (또는 E2E).
- **금지:** hidden 라벨 없이 700명에만 overfit한 하이퍼를 “최종 성능”으로만 제시.

## 8. 결론

중간 프로젝트는 **실측 UWB의 불량**으로 인해 Wi-Fi 가이드·기하 게이트·무결 Train CV라는 **단계적 시행착오**를 거쳐 V15에 도달하였다. 이 과정에서 얻은 핵심은 “높은 RMSE 숫자”가 아니라 **(1) 어떤 센서를 믿을 수 있는지, (2) 검증 튜닝과 무결 튜닝의 차이, (3) 복잡한 보정보다 구조가 맞는 단순화**이다.

기말 프로젝트는 **합성 RTT**라는 다른 전제 하에, Wi-Fi 가이드 없이 **18채널 RTT + 학습 + 강건 기하**로 전환한다. 이미 수행한 EDA에서 상관 0.82·Huber RMSE 19 m를 확인했으므로, 다음 단계는 **채널 보정 학습**과 **Train CV 기반 일반화**에 집중한다.
